# XmlDocMarkdown v3 Plan

## Snapshot

This plan reflects the current `v3` branch compared with `master` as of May 28, 2026. The branch currently sets `VersionPrefix` to `3.0.0` and `VersionSuffix` to `beta.1`, and includes a beta deployment commit.

## Changes Made So Far vs. master

### Package and Product Shape

- Consolidated the product down to one NuGet package: `XmlDocMarkdown.Core`.
- Removed the `Cake.XmlDocMarkdown` package project.
- Removed the `XmlDocMarkdown` .NET Framework console package project.
- Removed the `xmldocmd` global tool package project.
- Removed the deleted projects from the solution.
- Retargeted `XmlDocMarkdown.Core` from `netstandard2.0` to `net8.0`.
- Kept the command-line application implementation inside `XmlDocMarkdown.Core` through `XmlDocMarkdownApp.Run`, so a host can still call the app behavior programmatically.

### Build, Tooling, and Release Infrastructure

- Merged in the newer build template and build conventions.
- Moved to the .NET 8 SDK, C# 12, nullable reference types, implicit usings, embedded debug symbols, central package management, and latest analyzer settings.
- Updated package/test dependencies, including NUnit 4 and the current .NET test SDK line.
- Updated GitHub Actions to current checkout/setup-dotnet actions and to build/test on Ubuntu, Windows, and macOS.
- Kept publishing gated to the `ejball` repository on `master` from the Windows job.
- Updated the docs generation build target to run the net8.0 `XmlDocGen` helper.
- Added/adjusted warnings configuration, including the current ignore for `CA2201`.

### Public API and Input Model

- Replaced the old generator entry points that accepted an input path or `XmlDocInput` with a single public generator entry point:
  - `XmlDocMarkdownGenerator.Generate(Assembly assembly, string outputPath, XmlDocMarkdownSettings? settings)`
- Removed `XmlDocInput`, including separate `Assembly`, `AssemblyPath`, and `XmlDocPath` inputs.
- Removed `XmlDocAssembly` and introduced `XmlDocFile` as the parsed XML documentation container.
- Changed generation to require an XML documentation file next to the assembly, with `.xml` and `.XML` lookup, and to fail when the file is missing.
- Changed the command-line app to load the input by assembly name rather than accepting either a path or assembly name.
- Added a configuration callback to `XmlDocMarkdownApp.Run`:
  - `Run(IReadOnlyList<string> args, Action<string, XmlDocMarkdownSettings>? configure = null)`
- Kept `XmlDocMarkdownResult` as the summary of added, changed, removed files, and messages.

### Command-Line and Settings Surface

- Reduced command-line options to a small operational set:
  - `--clean`
  - `--dryrun`
  - `--quiet`
  - `--verify`
  - `--help`, `-h`, `-?`
- Removed command-line switches for settings that are still available only through programmatic configuration, including obsolete handling, unbrowsable/compiler-generated filtering, visibility, namespace pages, front matter, permalink style, external docs, and newline selection.
- Removed source-code link settings from `XmlDocMarkdownSettings` for now:
  - `SourceCodePath`
  - `RootNamespace`
- Removed generated Jekyll table-of-contents support from settings and implementation:
  - `GenerateToc`
  - `TocPrefix`
  - `XmlDocToc`
- Kept several generation settings available for programmatic callers, including `IncludeObsolete`, `SkipUnbrowsable`, `SkipCompilerGenerated`, `VisibilityLevel`, `NewLine`, `NamespacePages`, `FrontMatter`, `PermalinkStyle`, and `ExternalDocs`.

### Markdown Generation and Documentation Output

- Regenerated the checked-in documentation from the v3 generator.
- Removed the generated `XmlDocInput` documentation pages.
- Removed documentation pages for removed settings such as source-code path, root namespace, generated TOC, and TOC prefix.
- Removed Jekyll-specific docs site infrastructure from `docs`, including config, layout, assets, Docker Compose, and the docs landing page.
- Dropped the Jekyll table-of-contents generation path for now.
- Dropped source-code links in generated output for now.
- Refactored the markdown generator and related XML-doc model types around the simpler v3 API shape.

### Example Assembly and Tests

- Updated `tools/ExampleAssembly` to current C#/.NET conventions and regenerated its expected documentation.
- Removed the old `IsExternalInit` compatibility shim.
- Updated the test project for the new dependency/tooling baseline.
- Updated the smoke test to call the new `Assembly`-based generator API.
- Kept docs verification wired into the build test target.

## Steps to Finish v3

### 1. Capture the Settled v3 Contract

- Document that v3 intentionally ships only `XmlDocMarkdown.Core`.
- Document that the removed `xmldocmd`, `XmlDocMarkdown`, and `Cake.XmlDocMarkdown` packages are formally discontinued.
- Document the single supported usage pattern: consumers create a custom XmlDocGen-style host tool, reference the projects or assemblies to be documented, and call `XmlDocMarkdownApp.Run` with a configuration callback.
- Document that v3 targets only .NET 8 until .NET 8 goes out of service.
- Document that the v3 breaking API changes are intentional.
- Document that generation requires an XML documentation file next to the assembly, using the existing `.xml` and `.XML` lookup behavior.
- Document that explicit XML documentation paths and path-based assembly loading remain removed from the public API.
- Document that the trimmed command-line option surface is by design; consumers configure generation in code inside their custom host tool.

### 2. Update User-Facing Documentation

- Update `README.md` so it no longer advertises removed packages as current v3 deliverables.
- Move the useful docs-site content into the repository README.
- Rewrite the README around the single supported usage pattern: create a custom XmlDocGen host app with project references and configure generation in code.
- Add a v3 release-notes section describing the breaking package, target-framework, CLI, and API changes.
- Make sure generated API docs and hand-written docs agree on the supported v3 surface.

### 3. Strengthen Tests Around the New Contract

- Add tests for missing XML documentation files.
- Add tests for the remaining CLI flags and exit codes.
- Add tests for the `XmlDocMarkdownApp.Run` configuration callback.
- Add tests for dry-run, verify, quiet, and clean behavior.
- Add focused regression coverage for settings that are now programmatic-only.
- Add comprehensive unit-test coverage for markdown generation behavior and verify it with code coverage.
- Decide on a coverage reporting path and minimum acceptable coverage bar for the core library.
- Keep generated docs verification as part of the normal test path.

### 4. Validate Packaging and Release Behavior

- Run the full restore/build/test/docs verification flow locally.
- Pack `XmlDocMarkdown.Core` and inspect the package contents.
- Keep package validation enabled for the first stable v3 package.
- Keep `PackageValidationBaselineVersion` at `3.0.0` for the intentional major-version break.
- Keep the current beta/stable versioning flow.
- Confirm the publish workflow still matches the intended branch, tag, and repository rules.

### 5. Finalize the Stable Release

- Remove or update `VersionSuffix` when ready to ship stable v3.
- Update release notes and any remaining docs one final time.
- Regenerate docs and verify no generated files are stale.
- Run the full CI-equivalent build on all target platforms.
- Tag and publish the stable package.
- After publishing, verify NuGet metadata, package README, repository links, and generated docs links.
- Consider one final v2 patch release that points users toward the v3 package and usage model.

## Possible Future Directions

### C# and .NET API Coverage

- Keep the generator current with the latest C# compiler syntax and .NET API documentation conventions.
- Build and maintain a checklist of C# and .NET metadata shapes that should be represented correctly in generated docs.
- Add coverage for modern C# features that appear unsupported or incomplete today:
  - `record struct` and `readonly record struct` signatures.
  - `readonly struct`, `ref struct`, and `readonly ref struct` signatures.
  - `required` members and `init` accessors.
  - `in`, `ref readonly`, and `scoped` parameters and returns.
  - Function pointer types.
  - `static abstract`, `static virtual`, and `sealed` interface members.
  - Checked operators and unsigned right-shift operators.
  - Newer generic constraints such as `notnull`, `unmanaged`, nullable-qualified `class` constraints, `default`, and anti-constraints such as `allows ref struct`.
  - Primary constructors and any compiler-emitted members that affect public API documentation.
- Add an example type for each supported language feature so generated docs can be reviewed and regression-tested.
- Revisit the list when the project moves to a newer SDK or language version.

### Templated Markdown Generation

- Explore a templating model that gives consumers more control over how Markdown is built from generated documentation building blocks.
- Keep strong defaults so the current output remains easy to use without custom templates.
- Allow code-based configuration of templates and template data; a separate template file format is optional, not required.
- Evaluate `Fluid.Core` and Scriban as possible template engines.
- Define a stable object model for template input, including assemblies, namespaces, types, members, signatures, XML-doc blocks, links, and generated file names.
- Decide which output pieces should be independently templatable, such as assembly pages, namespace pages, type pages, member pages, signatures, parameter tables, examples, see-also sections, and front matter.
- Add snapshot or approval-style tests for default templates and representative custom templates.

### Test Quality and Coverage

- Grow the tests from smoke/regeneration checks into comprehensive unit tests for parsing, signature rendering, link generation, filtering, file output, and app behavior.
- Add code coverage collection to the build or CI pipeline.
- Use coverage reports to identify untested generator branches before stable releases.
- Add targeted regression tests for every newly supported C#/.NET API feature.
- Keep generated docs verification as an integration test, but make unit tests the primary way to diagnose rendering behavior.

### API Quality and Extensibility

- Introduce clearer internal building blocks if templating needs a structured representation of documentation output.
- Add extension points for link generation, page naming, front matter, filtering, and signature rendering when there is a concrete templating or configuration need.
- Consider immutable result objects or richer diagnostics if downstream host tools need more structured output.
- Review nullable annotations and XML documentation across the public API before declaring long-term stability.
